# Аутентификация и права доступа

## Две независимые системы

| | PlatformUser | AgentUser |
| --- | --- | --- |
| Кто | сотрудник в админ-панели | пользователь ИИ-агента в мессенджере |
| Вход | логин + пароль + код из письма | номер телефона из мессенджера |
| Права | `PlatformRole.permissions` | `AgentRole` определяет доступные темы |
| Токены | JWT access + refresh | нет, идентификация по chat id |

Общего кода у них нет намеренно: это разные аудитории с разными угрозами.

## Вход сотрудника

```
POST /auth/login { login, password }
    ├─ пароль неверен или логина нет → 401, одинаковый текст в обоих случаях
    ├─ аккаунт заблокирован          → 403, код не отправляется
    ├─ действующий код уже выслан    → 200 «Код подтверждения уже отправлен»
    └─ иначе → генерация 6 цифр, bcrypt-хеш в БД, письмо на почту

POST /auth/verify-2fa { login, code }
    ├─ код не запрашивался/истёк     → 401
    ├─ 3 неудачные попытки           → 429, нужен повторный /login
    └─ код верен → accessToken в теле + refreshToken в httpOnly-cookie
```

Решения и их причины:

* **Код хранится в виде bcrypt-хеша.** Дамп базы не даёт войти по чужому коду.
* **Ответ на неверный пароль и на несуществующий логин одинаков.** Иначе форма
  входа превращается в проверку существования учётной записи.
* **Заблокированный аккаунт не получает код.** Проверка статуса до отправки
  письма, а не после ввода кода.
* **Счётчик попыток и cooldown.** После трёх неверных кодов вход возможен
  только через 5 минут и повторный `/login`.

Время жизни: код — 15 минут, accessToken — 15 минут, refreshToken — 7 дней.
В режиме разработки оба токена живут год, чтобы не мешать отладке.

## Обновление сессии

```
POST /auth/refresh   (cookie refreshToken)
    ├─ куки нет / подпись неверна → 401 + сброс куки + запись в журнал
    ├─ пользователь удалён        → 401
    ├─ аккаунт заблокирован       → 401
    └─ иначе → новая пара токенов, обновление lastLogin
```

Проверка статуса аккаунта при обновлении обязательна: без неё выданный ранее
refresh-токен позволял бы заблокированному сотруднику продлевать сессию
неограниченно долго.

## Куки

```js
{
  httpOnly: true,                          // недоступна из JavaScript
  secure:   !isDev,                        // по http на localhost кука иначе отбрасывается
  sameSite: isDev ? 'lax' : 'none',        // прод: фронтенд на другом домене
  path: '/',
  domain: process.env.MAIN_DOMAIN
}
```

Флаги выставляются в `utils/auth-cookie.js` — одно место для установки и сброса,
чтобы `logout` гарантированно совпадал по атрибутам с `login`.

## Восстановление пароля

```
POST /password/forgot { email }
    → всегда 200 с одинаковым текстом
    → если аккаунт есть: случайный токен (32 байта), в БД sha256-хеш, срок 1 час
```

Одинаковый ответ и отсутствие токена в теле ответа — защита от перебора адресов.
Токен приходит только письмом. Если письмо не ушло, токен откатывается,
чтобы не оставлять «висящую» возможность сброса.

```
POST /password/reset/:token { password, confirmPassword }
    → поиск по sha256-хешу с непросроченным сроком
    → успешная установка пароля стирает токен (одноразовость)
```

## Проверка доступа к API

```
auth                       → есть ли валидный accessToken, жив ли аккаунт
checkPermission('...')     → есть ли право в роли пользователя
```

`auth` каждый раз читает статус пользователя из БД: блокировка действует
немедленно, не дожидаясь истечения access-токена.

`checkPermission` принимает строку или массив; при массиве нужны **все**
перечисленные права.

## Модель прав

Права — плоские строки вида `<ресурс>.<действие>`, сгруппированные для UI
в `constants/permissions.js`:

```
platformUsers.read|create|update|delete
agentUsers.read|create|update|delete
topics.read|create|update|archive|delete|approve
topicCategories.read|create|update|delete
platformRoles.read|create|update|delete
agentRoles.read|create|update|delete
logs.read
system_settings.read|update
files.upload
```

`ALL_PERMISSIONS` собирается из этой же структуры и используется:
как enum в модели роли, как enum в схеме валидации и как набор прав
системной роли. Один источник — расхождения невозможны.

## Системные сущности

Роль «Системный администратор» и созданный при старте администратор помечены
`isSystem: true`. Для них запрещены: удаление, смена прав роли, блокировка,
смена роли пользователя. Проверки живут в схемах валидации, поэтому нарушение
даёт `400` с понятным сообщением, а не `500`.
