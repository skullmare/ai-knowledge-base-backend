# Архитектура

## Состав системы

```
┌──────────────┐     HTTPS/WSS      ┌─────────────────────────────┐
│  Frontend    │ ─────────────────▶ │        Backend (Express)    │
│  (React)     │                    │                             │
└──────────────┘                    │  REST API      /api/v1/*    │
                                    │  WebSocket     /collaboration│
┌──────────────┐   long polling     │  Telegram-бот   (polling)   │
│  Telegram    │ ◀───────────────── │  MAX-бот        (polling)   │
│  MAX         │                    └───────┬─────────────────────┘
└──────────────┘                            │
                     ┌──────────────┬───────┼────────┬──────────────┐
                     ▼              ▼       ▼        ▼              ▼
                 ┌───────┐   ┌──────────┐ ┌────┐ ┌────────────┐ ┌──────┐
                 │MongoDB│   │  Qdrant  │ │ S3 │ │ OpenRouter │ │ SMTP │
                 └───────┘   └──────────┘ └────┘ └────────────┘ └──────┘
                  данные       векторы     файлы   LLM+эмбеддинги  почта
```

Backend — единственный компонент, который ходит во внешние системы.
Frontend и боты не знают ни про Qdrant, ни про S3.

## Слои

Запрос всегда проходит слои в одном направлении, снизу вверх никто не обращается.

```
routes/          какой URL, какие права, какая схема валидации
   ↓
middlewares/     auth → permission → validate
   ↓
controllers/     разбор validatedData, вызов сервисов, формирование ответа
   ↓
services/        работа с внешними системами и доменная логика
   ↓
models/          схемы Mongoose и правила целостности данных
```

Сквозные модули, доступные любому слою:

* `config/` — окружение и клиенты внешних систем;
* `constants/` — справочники прав, событий, наборов populate;
* `utils/` — форматирование ответа, логирование, пароли, хелперы запросов;
* `schemas/` — zod-схемы валидации входа.

### Почему именно так

* **Контроллер не знает про внешние системы напрямую.** Он вызывает
  `syncTopicToQdrant(topic)`, а не собирает точки и не дергает HTTP-клиент.
  Благодаря этому Qdrant подменяется одним моком в тестах.
* **Сервис не знает про HTTP.** В сервисах нет `req`/`res`, поэтому один и тот
  же код работает и в контроллере, и в обработчике сообщения из Telegram.
* **Валидация вынесена из контроллера.** Всё, что проверяемо до бизнес-логики
  (формат, существование связанных записей, уникальность, запрет на удаление
  системных сущностей), живёт в zod-схеме. Контроллер получает уже проверенные
  данные в `req.validatedData`.

## Ключевые потоки

### Вход в админ-панель

```
POST /auth/login       проверка пароля → генерация 6-значного кода → письмо
POST /auth/verify-2fa  проверка кода → accessToken (15м) + refreshToken (7д, httpOnly cookie)
POST /auth/refresh     проверка cookie и статуса аккаунта → новая пара токенов
```

Подробности — [auth.md](./auth.md).

### Жизненный цикл темы

```
создание (review) → совместное редактирование (WS) → одобрение (approved)
       ↑                                                      │
       └──────────── любая правка возвращает в review ◀────────┘
```

Одобрение — единственный момент, когда содержимое попадает в Qdrant.
Любая правка снимает индексацию и удаляет чанки. Подробности —
[knowledge-base.md](./knowledge-base.md).

### Ответ ИИ-агента

```
сообщение → история диалога → переформулировка запроса (LLM)
         → эмбеддинг → поиск в Qdrant с фильтром по роли
         → генерация ответа (LLM) → сохранение в историю
```

Фильтр по роли применяется на стороне Qdrant, а не после выдачи: пользователь
физически не может получить чанк темы, к которой у его роли нет доступа.
Подробности — [ai-agent.md](./ai-agent.md).

## Обработка ошибок

* Контроллеры перехватывают свои ошибки и отвечают через `utils/error-handler`.
* Всё, что не поймано (ошибка парсинга тела, превышение лимита размера,
  падение middleware), попадает в централизованный обработчик в `src/app.js`.
* Клиентские ошибки (< 500) отдают своё сообщение, серверные — обезличенное
  «Внутренняя ошибка сервера»; детали уходят только в лог.

Формат ответа всегда одинаков:

```jsonc
// успех
{ "success": true, "message": "...", "data": ..., "pagination": { ... } }
// ошибка
{ "success": false, "message": "...", "errors": [{ "path": "login", "message": "..." }] }
```

## Запуск и остановка

`server.js` выполняет строгую последовательность:

1. проверка обязательных переменных окружения (в проде — падение при отсутствии);
2. подключение к MongoDB;
3. сиды: системная роль → системный администратор;
4. синхронизация индексов `AgentUser` (снос устаревших уникальных индексов);
5. инициализация коллекции и payload-индексов Qdrant;
6. загрузка сервера совместного редактирования;
7. запуск ботов;
8. `app.listen`.

Остановка по SIGTERM/SIGINT: закрытие HTTP-сервера (с таймаутом 10 с),
затем закрытие соединения с MongoDB.
